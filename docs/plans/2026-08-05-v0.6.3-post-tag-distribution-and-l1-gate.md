# v0.6.3 post-tag distribution sync and L1 release-gate plan

> **Historical status (2026-08-20):** This plan records the v0.6.3 release
> work as it was scoped. The later decision to decouple distribution evidence
> from L1 means missing Homebrew smoke evidence blocks the Homebrew tap gate,
> not L1. The historical steps below are retained unchanged; current scope is
> defined by `ROADMAP.md` and `docs/release-readiness.md`.

## Objective

Finish the distribution work that can only be performed from the published
`v0.6.3` Release, then decide the L1 production-enable gate from a replayable
evidence packet. This plan does not change language-analysis runtime behavior
or add release CI infrastructure.

## Observed starting point (2026-08-05)

- Remote tag `v0.6.3` and its public GitHub Release exist.
- Release workflow run `30986456993` completed successfully and published all
  four binaries, their `.sha256` sidecars, and `THIRD_PARTY_NOTICES.md`.
- npm registry `latest` is `@iliasalmerekov/aegis@0.6.3`.
- The checked-in Homebrew formula and npm checksum file still pin `v0.6.2`;
  they must be generated from the real v0.6.3 assets, never guessed before
  publication.
- This host is Linux x86_64. macOS Homebrew evidence must be supplied by the
  release operator on a real macOS host.

## Locked boundaries

- The Aegis-repository commit contains only v0.6.3 generated distribution
  pins, release evidence, and any justified L1/release-readiness status
  changes. It excludes the unrelated untracked `landing/` files.
- `IliasAlmerekov/homebrew-aegis` receives one separate formula-only commit.
- The macOS smoke is an operator step, not justification to introduce a new CI
  job or runner contract.
- L1 is marked production-enabled only after every evidence item below and a
  clean Standards/Spec review plus adversarial re-review. A successful tag by
  itself is insufficient.
- No new ADR or glossary term is needed: this applies the existing
  distribution contract and ADR-022's release-enablement rule.

## Evidence packet and execution order

### 1. Preserve the release boundary and verify immutable assets

1. Record `git status --short` and keep `landing/DESIGN.md`, `landing/images/`,
   `landing/theme.css`, and `landing/tokens.json` outside every staging set.
2. Verify the public `v0.6.3` Release is non-draft and contains exactly the
   four target binaries, four matching checksum sidecars, and
   `THIRD_PARTY_NOTICES.md`.
3. Run the opt-in `release_assets_live` test against `v0.6.3`; retain its
   output, including checksum verification, as release evidence.
4. Use the successful tagged workflow as the release-build and publish
   evidence. Do not substitute a later branch workflow for the tagged artifact.

### 2. Regenerate repository distribution metadata from the Release

1. Run `scripts/update-npm-package.sh v0.6.3` and inspect the resulting
   `packaging/npm/checksums.json` against the downloaded v0.6.3 sidecars.
2. Run `scripts/update-homebrew-formula.sh v0.6.3`; inspect all four target
   URLs and hashes plus the `third_party_notices` resource. The formula must
   install the notice below `share/doc/aegis`.
3. Run focused contract tests for the npm package, Homebrew formula, release
   workflow, and live release assets. Run the documented full workspace,
   formatting, clippy, audit, and deny gates if any Rust/test contract source
   changes; otherwise record the focused docs/packaging verification honestly.
4. Perform a Linux registry install of `@iliasalmerekov/aegis@0.6.3` into an
   isolated prefix and assert `aegis --version` is `0.6.3`.

### 3. Publish and validate the Homebrew formula

1. Commit the generated formula in the Aegis repository together with its
   matching v0.6.3 checksum file and evidence documentation, but only after the
   preceding checks pass.
2. Copy that exact generated formula into
   `IliasAlmerekov/homebrew-aegis/Formula/aegis.rb`, commit it separately, and
   push the tap's default branch.
3. On Linux, cleanly retap and run the documented `brew audit --strict --online`,
   `brew install`, `brew test`, and `aegis --version` checks against the public
   tap. Confirm the installed `share/doc/aegis/THIRD_PARTY_NOTICES.md` exists.
4. The release operator repeats the same install/test/version/notice checks on
   a real macOS host and supplies the commands and complete result. Failure or
   unavailable macOS evidence leaves L1 open; it is not replaced by a Linux
   result.

### 4. Review and close only what the proof supports

1. Add concise, timestamped v0.6.3 evidence to `docs/release-readiness.md`.
   Update `PROJECT_STATE.md`, `CHANGELOG.md`, and the relevant L1 roadmap and
   release-readiness checkboxes only after all stated evidence is green.
2. Run `code-review` on the Aegis-repository diff against this plan and the
   Iteration 10 FINAL GATE, then run `re-review`. Fix only confirmed findings
   and repeat the bounded review cycle as required.
3. If every FINAL GATE requirement and both platform smoke records are present,
   mark the four L1 adapters production-qualified/default-on for the release.
   If any item is missing, publish only the proven distribution metadata and
   leave L1 and the corresponding release-readiness items open with the precise
   blocker recorded.

## Completion criteria

- v0.6.3 npm checksums and the Aegis formula are generated from live release
  assets, not hand-entered.
- The public Homebrew tap contains that exact formula and Linux plus operator
  macOS smoke evidence proves binary, test, version, and notice delivery.
- The evidence packet links the tagged workflow, live asset validation, npm
  install, both Homebrew smokes, and a clean review/re-review cycle.
- No unrelated `landing/` content enters either commit.
- L1 status reflects the evidence exactly: closed only on full proof, otherwise
  explicitly open.
